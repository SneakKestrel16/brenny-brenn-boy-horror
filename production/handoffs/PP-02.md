## Bugs found and how the spike handles them

1. **Godot 4.7.2 engine bug: `ENetMultiplayerPeer.create_server(port, clients, max_channels)`**
   passes `max_channels + 3` as the server's **incoming bandwidth** (arguments shifted by one in
   `modules/enet/enet_multiplayer_peer.cpp:67`, read from the 4.7.2-stable source). So
   `max_channels = 4` advertised 7 bytes per second.
   - Mechanism, measured by logging `PEER_PACKET_THROTTLE` and `_LIMIT`: each client's ENet
     bandwidth throttle set its limit to 1 about 1 s after joining. Unreliable (voice) packets were
     then dropped until the RTT throttle climbed back to 32 at about 16 s, so 20 to 40% of a
     client's voice was lost on loopback.
   - Fix: `create_server(port, max_clients)` (max_channels 0 = unlimited) while clients ask for 4
     channels. Loss went to 0.
   - On the way I tried and **disproved** two other explanations: pinning the RTT throttle (no
     change while the bandwidth limit was wrong) and unsequenced vs ordered sends (a chance result;
     voice is back to plain unreliable per doc 06).
   - Not reported upstream (Q-009).
2. **ENet's RTT throttle drops unreliable packets after a hitch.** In one windowed run, a start-up
   hitch cost 37 frames. With a forced 300 ms hitch (`--stall-at`), ENet's default lost 4 and 13
   frames; with `throttle_configure(5000, 2, 0)` it lost 0 and 0. The spike pins it.
   `--enet-throttle` restores the default for comparison over the real internet.
3. **The first-import crash (Q-008), diagnosed as far as the tools allow.**
   - Reproduced: a clean headless `--editor --quit` segfaults (exit 139) on 5 of 5 fresh copies.
     The control without the addon passed 2 of 2.
   - What makes it go away: running the editor 60 frames or more (`--quit-after 60/120/200` pass,
     `--quit-after 30` crashes), or pre-seeding `.godot/extension_list.cfg`, which passed. So it
     happens when the editor quits soon after registering the extension mid-scan.
   - What doesn't matter: `reloadable = true` and the release DLL in the editor still crash.
   - Hypothesis **disproved**: I suspected TwoVoIP's mismatched init levels (it registers classes
     at SERVERS but declares a minimum of SCENE), but a tool probe shows its classes registered in
     that session.
   - No native stack trace: no debugger is installed, and there's no Windows Error Reporting event.
   - **Recommendation: keep v6.5 pinned.** Runtime is unaffected, the workaround is one file, and
     v6.6 is worse (#107).
   - **Exported build: not affected** (measured 2026-10-06 after Q-009's templates; D-014). It
     never runs the editor import.
4. **A plain run never loads the addon without `.godot/extension_list.cfg`.** A fresh folder
   without an editor import fails to parse `TwovoipOpusEncoder` and hangs. The friend package
   seeds the file.
5. **`UPNP.discover()` returned success with 0 devices**, so `get_gateway()` printed an engine
   `ERROR`. The spike now checks `get_device_count()` first.
6. **Shutdown errors and leaks:** a send to a peer that's mid-disconnect printed
   `Unable to send packet on channel 0`, and quitting before the audio thread dropped the WAV
   playback leaked it. Both are fixed: the host checks each peer's state before sending, and stops
   players and waits 0.1 s before quitting.
7. **Tested and wrong, so not used:** I assumed RNNoise would suppress the synthetic voices. It
   doesn't: it sent the same frames as denoise off, so WAV input keeps RNNoise like the mic.
